# 修复记录 1.0.16 —— 创意工坊上传前审计

本次不是玩法更新，而是"准备上 Steam 创意工坊"这件事本身带来的审计：上传会公开模组目录里的每一个文件、
会把 `info.ini` 连同 `publishedFileId` 交给 Steam、会让别的玩家在自己的存档里跑这套代码。
所以这一版处理的是**会外泄的东西**、**上传后会持续出错的东西**、以及**玩家遇到就再也不会用的问题**。

---

## 一、先核实游戏侧的事实（反编译 IL，非猜测）

用 `tools/AssemblyInspector` 读了 `Duckov_Data\Managed\Assembly-CSharp.dll` 的实现：

| 事实 | 证据 | 结论 |
| --- | --- | --- |
| `info.ini` 的 `description` 读取时会过 `Regex.Unescape` | `Duckov.Modding.ModManager.TryProcessModFolder` | 反斜杠会被当转义序列解释；我们的描述里没有反斜杠，安全 |
| `publishedFileId` 解析失败只 `LogError`，不拒绝加载 | 同上 | 手改坏了不会白屏，但那一行会失效 |
| `publishedFileId == 0` 时上传会 `RequestNewWorkshopItemID()` | `SteamWorkshopManager+<UploadWorkshopItem>d__32::MoveNext` | **info.ini 里没有 id 就是"新建条目"，有 id 才是"更新"**；上传器随后把新 id 写回 info.ini |
| 上传是 `SetItemContent(模组目录)` 整目录打包 | 同上 | 目录里的任何残留文件（旧日志、备份、截图）都会公开 |
| 封面固定取 `preview.png` | `SetItemPreview("preview.png")` | 封面文件名不可配置，尺寸建议 512×512 |
| `SetItemTags` 第二次调用硬编码 `"Mod"` | 同上 | `info.ini` 里写的标签在工坊侧会被覆盖成 `Mod`；且 `Quality of Life` / `Utility` 这两个标签在游戏程序集里根本不存在 |

结论：**上传前必须做的事是把模组目录收拾干净、把 id 写对、封面换大**，而不是改玩法。

## 二、已修：上传会出事的部分

1. **日志不再写进模组目录**（`src/DuckovSharedBike/ModBehaviour.cs:317` `OpenLogFile()`）
   旧版日志写在 `info.path/logs/bootstrap.log`，实测 366KB / 2866 行，含本机绝对路径和玩家坐标——上传即公开。
   现在优先写 `Application.persistentDataPath/DuckovSharedBike/logs/bootstrap.log`
   （即 `%USERPROFILE%\AppData\LocalLow\TeamSoda\Duckov\DuckovSharedBike\logs`），失败才退回模组目录；
   `RotateLogIfLarge()`（`:348`）在超过 1MB 时轮转成 `bootstrap.log.1`，防止长期游玩堆到几百 MB。
   F9 面板（`:264`）现在显示日志真实位置，不再假定在模组目录。

2. **版本号不再写死**（`ModBehaviour.cs:16`、`:361`）
   旧版 `const string Version = "1.0.9"` 与实际版本脱节，日志里一直印 1.0.9。改为读
   `AssemblyInformationalVersion`（截掉 `+` 之后的构建元数据），退回程序集版本，再退回 `unknown`。

3. **安装脚本保留工坊条目 id**（`scripts/Install.ps1`）
   安装会覆盖 `info.ini`。若旧 `info.ini` 里有 `publishedFileId`，脚本记住它，并在 SHA256 校验**之后**追加回去——
   否则下一次上传会被当成新条目，工坊里出现两条一模一样的模组。
   同时删除安装目标里的旧 `logs` 目录。

4. **诊断收集脚本跟着新日志位置走**（`scripts/Collect-Diagnostics.ps1`）
   从 `Duckov_Data/app.info` 前两行读 `company` / `product`，拼出用户数据目录；
   找不到才退回模组目录，都没有就写一份说明文件，不再抛异常。

5. **封面 512×512**（`scripts/Make-Preview.ps1` 加 `-Scale`）
   原脚本在 256×256 上画，工坊缩略图看着发糊。现在默认 2 倍超采样输出 512×512，版式与文字沿用 256 坐标。

## 三、已修：玩家一遇到就退游的问题

6. **单车场景异常后能自己回来**（`BikeWorldController.cs:1102` `TryRecoverWorldFault()`、`:1114` `ReenableAfterFault()`）
   旧版任一帧异常 → `_worldFailed=true` 且永不解除，整个模组静默失效，只能重开游戏。
   现在按 10 秒（前 3 次）/ 120 秒退避重试，切场景重置计数；F9 面板多出"重新启用单车"按钮，
   面板文本显示 `FaultSummary`（`:64`）。

7. **诊断面板不会因一次异常整块消失**（`ModBehaviour.cs:229`、`:283`）
   旧版 `OnGUI` 一抛异常就 `_panelFailed=true`，HUD、诊断面板、脱困按钮一起消失且不恢复。
   现在只有面板本体在 try 里，失败 5 秒后重试；HUD 单独 try，日志 10 秒去重。

8. **租车按钮不会把 UI 打死**（`BikeWorldUI.cs:132`）
   记录 `DrawStation` 的按钮异常（"租车未完成，请保留日志后重试。"），不再让异常逃出 `OnGUI`。

9. **账单缺记录不再整页空白**（`BikeWorldUI.cs:178`）
   `Rentals.Single(...)` 改 `FirstOrDefault` + 跳过该行，避免一条坏记录让账单面板永远画不出来。

10. **死亡时立刻落盘**（`NativeRentalRuntime.cs:594` `OnDeath`）
    旧版死亡只 `CacheState`，玩家在死亡界面退游戏会读回旧档：2000 赔偿丢失、租约"复活"。
    现在死亡路径 `Persist(true)`，失败只记录不抛。

11. **收据损坏不再永久封锁付款**（`NativeRentalRuntime.cs:208`、`:216`）
    旧版收据校验失败即 `Faulted=true` 并持久化，之后 `Pay` 永远返回 `PaymentBusy`，钱永远欠着。
    现在：空/缺失视为"未损坏"（重建），`SaveId` 变了也重建；只有真正的校验失败才隔离；
    另外加了一次自愈——若已无待清算订单却还挂着故障标记，自动清掉。

12. **受击立刻下车**（`BikeWorldController.cs:755` `OnRiderDamaged`、`:773` `ForceDismountOnDamage`）
    骑车被打时不再连同自行车一起被拖走：置标记，下一帧找安全落点、解除骑行、提示"受到伤害，已立刻下车"。
    伤害钩子整体 try/catch，绝不把异常抛回游戏的受击流程。

13. **远距离位移不再拖着车走**（`BikeWorldController.cs` `LateTick`）
    传送/瞬移（>15m）时结束骑行、车留在原地并继续计费；≤15m 的位移视为正常骑行跟随。

14. **上车判定放宽**（`BikeWorldController.cs:806`–`:835`、`FindLanding`）
    旧版二次校验要求落点离车 <0.2m 且严格寻地，车停在路沿/斜坡/墙边就"点了没反应"。
    现在：距离 >3.2m 才拒绝；先用宽松寻地，再按 8 个方向试 0.55m 环；落点容差 0.9m（最差 1.2m）；
    车距过近只给建议日志，不再直接失败。失败必定有中文提示 + 日志原因（`FailMount`，`:743`）。

15. **F 键不再误触发**（`BikeWorldController.cs:270` `NativeUiOpen()`、`:152`）
    打开原生界面（背包/仓库/对话）时不再响应 F5–F8 热键。

16. **固定站点冲突不再抛异常**（`CreateTestPlacements`）
    旧版 `throw new InvalidOperationException("Fixed station ID conflicts with saved layout.")` 会被 Tick 捕获 →
    整个单车场景停摆。现在跳过冲突站点 + 提示"有站点与存档布局冲突，已跳过；详见日志。"

## 六、这次的工程事故与恢复（必须记录）

改 `BikeWorldController.cs` 里一行时用了
`(Get-Content …) -replace … | Set-Content -Encoding UTF8`：Windows PowerShell 以 GBK(936) 读 UTF-8，
写出后全文件中文变乱码（284 个编译错误）；随后 `git checkout --` 把该文件回退到 1.0.11 提交，
**1.0.12–1.0.16 对该文件的未提交改动全部丢失**（且事故前的成品 DLL 已被下一次构建覆盖）。

恢复方式：
1. 以 `artifacts\DuckovSharedBike-1.0.15.zip` 里的 DLL 为基准，用 `tools/AssemblyInspector` 逐方法 dump IL；
2. 按 `docs/修复记录-1.0.12.md` / `1.0.13` / `1.0.14` / `1.0.15.md` 的记录补回语义；
3. 新增 `scripts/Compare-DllIl.ps1`，把基准 DLL 与当前构建做逐指令比对（归一化分支地址与编译器生成的闭包编号）。

最终比对结果（`artifacts/verification/il-diff-2.txt`）：BikeWorldController 105 个方法中，
不相同的 11 个恰好是本版**有意**的改动（Tick、LateTick、CreateTestPlacements、CreatePlannedPlacements、
RefreshNativeTravelPoints、NearestStation、RecoverWorldFault、DestroyActors、DrawStation、DrawInvoices、.ctor），
其余方法指令与 1.0.15 完全一致（含 `Return`、`Summon`、`AllowTravel`、`PrepareSessionExit` 等）。

规矩定下来：**C# 源码只用编辑工具改，绝不用 PowerShell 整文件重写**；改代码前先把 `bin` 产物复制一份进
`artifacts/snapshots/`。

## 八、上传创意工坊前还需要人做的三件事

1. **在真机完整跑一遍**（开局 → 租车 → 骑到掉血 → 还车 → 欠费 → 召车 → 传送），
   本版代码改了上车判定与伤害下车，这是最需要手感验证的两处。
2. 上传前确认 `mod/info.ini` **没有** `publishedFileId`（首传新建条目）或**有正确的 id**（更新已有条目）；
   上传后游戏会把 id 写回 `info.ini`，请提交进仓库。
3. 工坊页面标签会在上传时被游戏改写成 `Mod`，别在 `info.ini` 里花心思写标签；封面用 `preview.png`（512×512）。
